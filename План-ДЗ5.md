## Выбранные индикаторы

Три SLI, все на метриках, реализованных в ДЗ-4 (как требует задание), и оба
подхода из задания представлены: два request-based, один time-based.

| # | SLI | Источник | Подход |
|---|---|---|---|
| 1 | Доступность API — доля не-5xx ответов на пользовательских маршрутах | `sentinel_http_requests_total` | RBSLO |
| 2 | Скорость API — доля запросов быстрее 300 мс | `sentinel_http_request_duration_seconds_bucket` | RBSLO |
| 3 | Живость конвейера проверок — доля минут, в которые воркер выполнял проверки | `sentinel_probes_total` | TBSLO |

Почему не «успешность проверок»: `sentinel_probes_total{result="down"}` означает,
что упал **чужой** сайт, а не наш сервис. Как SLI годится не успешность проверок,
а их темп и свежесть — иначе мы бы мерили доступность клиентских целей.

Метка `service` (`sentinel-api`, `sentinel-worker`) навешивается реестром метрик
на все серии — в запросах используем её, а не `app` из лейблов пода.

### Формулы SLI

```promql
# SLI-1 доступность, окно $w
sum(rate(sentinel_http_requests_total{service="sentinel-api",route!~"/healthz|/readyz|unmatched",status!~"5.."}[$w]))
/ sum(rate(sentinel_http_requests_total{service="sentinel-api",route!~"/healthz|/readyz|unmatched"}[$w]))

# SLI-2 скорость, окно $w
sum(rate(sentinel_http_request_duration_seconds_bucket{service="sentinel-api",le="0.3",route!~"/healthz|/readyz"}[$w]))
/ sum(rate(sentinel_http_request_duration_seconds_count{service="sentinel-api",route!~"/healthz|/readyz"}[$w]))

# SLI-3 хорошие минуты конвейера, окно $w
avg_over_time((sum(rate(sentinel_probes_total[1m])) > bool 0)[$w:1m])
```

### SLO (окно 30 дней, скользящее)

| SLO | Цель | Бюджет ошибок на 30 дней |
|---|---|---|
| Доступность API | 99.5 % | 0.5 % запросов, около 3 ч 36 мин полного простоя |
| Скорость API (доля < 300 мс) | 95 % | 5 % запросов |
| Живость конвейера | 99 % минут | 7 ч 12 мин |

Бюджет и скорость выгорания:

```promql
# остаток бюджета ошибок
1 - (1 - <SLI>) / (1 - <SLO>)

# burn rate на окнах 1 ч и 6 ч
(1 - <SLI_1h>) / (1 - <SLO>)
```

### SLA

Внешнее обещание, календарный месяц: доступность API **99.0 %**,
p95 времени ответа не выше **500 мс**.

Исключения: объявленные окна обслуживания, недоступность чужих целей
мониторинга (это не наш отказ).

Запас между SLO 99.5 % и SLA 99.0 % сделан намеренно: бюджет ошибок выгорает
раньше, чем нарушается обещание пользователю.

Сводный SLA по трём SLO как произведение независимых:
`0.995 * 0.95 * 0.99 = 0.9358`. В отчёте — с оговоркой: перемножать осмысленно
только однородные индикаторы доступности, иначе «скорость» тянет общий
показатель вниз без реального смысла.

### Откуда взяты цифры (решение принято)

Цели — отраслевые дефолты с поправкой на архитектуру стенда. Замер базовой
линии решено не делать, цифры приняты как есть и дальше не пересматриваются.

| Цифра | Основание |
|---|---|
| 99.5 % доступности | дефолт между 99 % и 99.9 %, сдвинут вниз от трёх девяток: один инстанс PostgreSQL, rolling update без PDB, одна нода minikube |
| 300 мс | правило большого пальца для веб-взаимодействия, типовой диапазон API-SLO 200–500 мс |
| 95 % быстрых запросов | конвенция «целимся в p95» |
| 99 % минут конвейера | воркер опрашивает базу раз в секунду, провалы при деплое — десятки секунд; 7 ч 12 мин бюджета перекрывают их с запасом |
| SLA 99 % за месяц | проектное решение: обещание пользователю мягче внутренней цели |
| бюджеты ошибок, burn rate | арифметика из цели и окна, не конвенция |

Формулировка для отчёта: цели SLO объявлены на основании отраслевых практик
и ограничений стенда; базовая линия за полное 30-дневное окно не наблюдалась,
поэтому цели подлежат пересмотру после первого полного окна.

Следствия:

- порог 300 мс финальный, значит шкала бакетов из шага 1 остаётся с краем `0.3`;
- порог мягкий относительно простых маршрутов (селект из локальной базы),
  поэтому в спокойном состоянии SLI-2 будет близок к 100 % — это нормально,
  но демонстрация должна пробивать порог гарантированно: задержка в chaos
  на шаге 9 берётся 800 мс, а не 200–300 мс.

Порог 300 мс из SLO-2 должен быть точным краем бакета, иначе `le="0.3"`
в запросе не существует: в `prometheus.DefBuckets` есть 0.25 и 0.5, но не 0.3.

Правка в `internal/infra/metrics/http.go` — заменить `Buckets: prometheus.DefBuckets`:

```go
		duration: factory.NewHistogramVec(prometheus.HistogramOpts{
			Namespace: namespace,
			Name:      "http_request_duration_seconds",
			Help:      "Время обработки HTTP-запроса.",
			// Шкала подогнана под SLO скорости: нужен точный край 0.3 с.
			// В DefBuckets ближайшие края — 0.25 и 0.5, и доля быстрых
			// запросов считалась бы по чужому порогу.
			Buckets: []float64{0.025, 0.05, 0.1, 0.2, 0.3, 0.5, 1, 2.5, 5},
		}, []string{"method", "route"}),
```

Линтер: литерал прямо в поле структуры безопасен (`mnd` не заглядывает внутрь
composite literal), а `var` на уровне пакета поймал бы `gochecknoglobals` —
исключения для него прописаны только для `apierrors.go` и `prober/guard.go`.

Тест в `internal/infra/metrics/metrics_test.go` (хелперы `find` и `labels` там есть):

```go
func TestHTTP_HistogramHasSLOBucket(t *testing.T) {
	t.Parallel()

	registry := metrics.NewJobRegistry(testService)
	metrics.NewHTTP(registry.Registerer()).
		RequestFinished(http.MethodGet, "/healthz", http.StatusOK, 250*time.Millisecond)

	histogram := find(t, registry,
		"sentinel_http_request_duration_seconds", labels{"route": "/healthz"}).GetHistogram()

	bounds := make([]float64, 0, len(histogram.GetBucket()))
	for _, bucket := range histogram.GetBucket() {
		bounds = append(bounds, bucket.GetUpperBound())
	}

	require.Contains(t, bounds, 0.3, "SLI скорости считается по краю 0.3 с")
	require.Equal(t, uint64(1), histogram.GetSampleCount())
}
```

Смысл теста — защита порога: если кто-то вернёт `DefBuckets`, запрос SLI тихо
начнёт считать не то.

Проверка:

```bash

```

```bash
curl -s http://localhost:9091/metrics | grep http_request_duration_seconds_bucket | grep 'le="0.3"'
```

Грабля: смена шкалы меняет набор серий `_bucket`, старые данные в VM остаются

это ещё и практичнее: на 30-дневном окне двухминутная деградация не видна.

## Шаг 4. Сценарий пробера

Статус: `[x]` сделано

`internal/blackbox/journey.go` — отдельно от `internal/infra/prober` (тот ходит
по чужим сайтам и имеет SSRF-guard, нам же нужен свой кластерный адрес).

Шаги (значения метки `step` в метриках): `healthz`, `readyz`, `login`,
`monitors`, `status_page`. Сценарий успешен только если прошли все шаги.

API пакета: `New(metrics, logger, Options)`, `Run(ctx)` — цикл по тикеру,
`RunOnce(ctx) bool` — один прогон. Порт `blackbox.Metrics` описан в пакете
и реализуется `metrics.SLI` из шага 3.

Принятые решения:

- **первый прогон идёт сразу, до первого тика.** Иначе свежеподнятый пробер
  до `PROBER_INTERVAL` выглядит в графиках как «нет данных»;
- **список мониторов запрашивается и при неудачном входе**, с пустым токеном.
  Без входа пользователь списка тоже не увидит, так что шаг обязан стать
  неуспешным. Если бы шаг пропускался, его gauge застыл бы на последнем
  удачном значении и показывал бы здоровье при сломанном сервисе;
- **ответ 200 без токена — тоже отказ шага входа**: дальше идти нечем. Токен
  достаётся через `check`-замыкание, поэтому отказ попадает и в метрику шага,
  и в результат сценария, а не только в сценарий;
- **шаг публичной страницы пропускается при пустом slug** — и тогда его метрик
  нет вовсе, а не ноль: отсутствие шага не должно выглядеть как отказ;
- таймаут одного шага — `http.Client.Timeout`, тело ответа читается с лимитом
  64 КиБ.

Тесты (`internal/blackbox/journey_test.go`, 7 штук, на `httptest`): все шаги
прошли; падение одного шага не ломает остальные; неудачный вход помечает шаг
мониторов неуспешным; 200 без токена; пустой slug пропускает шаг и не трогает
метрики; медленный ответ сверх таймаута — отказ; отмена контекста выходит
из цикла.

`go test ./internal/blackbox/...` — ok, `gofmt` чисто. Линтер даёт 4 замечания
`wrapcheck` на `fmt.Errorf`/`errors.New` — ровно тот же шаблон, что уже есть
в `internal/config/checks.go` и `internal/infra/metrics/push.go`; правится
одной строкой в `.golangci.yml` (`ignore-sigs`), если захотим чистый `make lint`.

## Шаг 7. vmalert + recording rules

Статус: `[x]` манифесты готовы, осталось применить на кластере

`k8s/monitoring/sli-rules.yaml` — ConfigMap с правилами,
`k8s/monitoring/vmalert.yaml` — Deployment и Service (NodePort 30880).
vmalert читает из vm-single и пишет результат обратно туда же, так что
записанные ряды лежат рядом с исходными метриками.

Ключевое решение: **серии различаются меткой `slo`, а не именем метрики.**
Имя одно — `sentinel:sli:ratio5m{slo="availability"|"latency"|"pipeline"|"journey"}`,
цель — `sentinel:slo_target:ratio{slo=...}`. За счёт этого остаток бюджета
и burn rate считаются **одним правилом на все SLO сразу**, через совпадение
меток:

```promql
sentinel:error_budget_remaining:ratio30d = 1 - (1 - sentinel:sli:ratio30d) / (1 - sentinel:slo_target:ratio)
sentinel:burn_rate:ratio1h              = (1 - sentinel:sli:ratio1h)  / (1 - sentinel:slo_target:ratio)
```

Что записывается:

| Ряд | Окно | Для чего |
|---|---|---|
| `sentinel:slo_target:ratio` | — | цель SLO как серия: линия на графике берётся из одного места |
| `sentinel:sli:ratio5m` | 5 мин | графики, в том числе вспомогательный `slo="journey"` от пробера |
| `sentinel:sli:ratio1h`, `:ratio6h` | 1 ч, 6 ч | burn rate на двух окнах |
| `sentinel:sli:ratio30d` | 30 дней | окно SLO, на нём считается бюджет |
| `sentinel:error_budget_remaining:ratio30d` | 30 дней | 1 — бюджет целый, 0 — исчерпан, ниже нуля — SLO нарушено |
| `sentinel:burn_rate:ratio1h`, `:ratio6h` | 1 ч, 6 ч | во сколько раз быстрее нормы тратится бюджет |
| `sentinel:sla_compound:ratio30d` | 30 дней | сводный SLA |

Две группы с разным интервалом: `sentinel-sli` раз в 30 с (короткие окна
и burn rate), `sentinel-slo` раз в 5 минут (6 ч, 30 дней, бюджет, сводный SLA) —
запрос по 30-дневному окну дорогой, и гонять его каждые полминуты незачем.

Детали, до которых дошёл по ходу:

- `increase` вместо `rate` на 30-дневном окне: считаем события за окно,
  а не их темп;
- 30-дневные окна для конвейера считаются не по сырым метрикам, а поверх
  записанного `ratio5m` — иначе подзапрос `[30d:1m]` на каждом прогоне
  перемалывает 43 тысячи точек;
- сводный SLA — произведение трёх SLI, а прямого умножения серий между собой
  в MetricsQL нет, поэтому `exp(sum(ln(...)))`;
- `-notifier.blackhole=true`: правил оповещения нет, только recording rules,
  и без заглушки notifier процесс не стартует;
- `max(sentinel_sli_journey_success)` — на случай переката пробера, когда
  серий на короткое время две.

Цели в Makefile:

```bash
make rules-up       # apply правил + vmalert, ждёт rollout
make rules-reload   # применить изменённые правила и перезапустить vmalert
make vmalert-ui     # проброс порта, статус правил на http://localhost:8880
```

Проверено здесь: манифесты — `kubeconform -strict` (3 ресурса, ошибок нет);
сами правила — `vmalert -dryRun` в контейнере `victoriametrics/vmalert:v1.154.0`,
код возврата 0, то есть и схема правил, и все выражения MetricsQL разобраны.
На кластере не применялось: minikube не поднят.

## Шаг 9. Изменения приложения для скринкаста

Статус: `[x]` сделано

`internal/transport/http/middleware/chaos.go` — управляемая деградация,
выключена по умолчанию. Переменные: `CHAOS_ERROR_RATE` (доля ответов 503),
`CHAOS_LATENCY` с `CHAOS_LATENCY_RATE`, `CHAOS_READYZ_FAIL`.

Решения:

- **сбои вносятся только в `/api/`.** Проверки живости не трогаются: 503
  на `/healthz` заставит kubelet перезапускать поды, и вместо управляемой
  деградации выйдет падение с CrashLoop. Для `/readyz` есть отдельный
  переключатель — он нужен, чтобы показать вывод пода из балансировки;
- **middleware ставится последним в цепочке** (после `Metrics` и `Logger`):
  внесённый сбой обязан попасть и в метрики, и в логи, иначе SLI его не увидит;
- **в production включение запрещено** — `checkChaos` в `internal/config/checks.go`,
  по образцу `checkTargets`;
- **задержка без доли запросов отвергается на старте**: `CHAOS_LATENCY=800ms`
  без `CHAOS_LATENCY_RATE` никого не задержала бы, и это молчаливая опечатка
  в демонстрации;
- middleware включается в цепочку только если что-то задано: `ChaosConfig.Enabled()`.

Скрипты:

- `scripts/slo-load.sh [BASE_URL] [RPS]` — фоновая нагрузка, на ней считаются
  request-based SLI; при 401 перелогинивается сам, по Ctrl+C печатает итог;
- `scripts/chaos.sh` — переключение режимов, по умолчанию через
  `kubectl set env deploy/api`, с `MODE=compose` — через пересоздание
  контейнера api. `off` в k8s убирает переменные (минус в конце имени),
  а не выставляет нули.

Цели: `make load`, `make chaos ARGS="errors 0.3"`.

### Сценарий скринкаста

```bash
make up && make demo          # окружение и демо-данные
make load                     # в отдельном окне: нагрузка
```

1. **базовая линия** — все SLI около 100 %, бюджет целый, burn rate около нуля;
2. `scripts/chaos.sh errors 0.3` — падает SLI-1 доступности, горит бюджет,
   растёт burn rate; SLI-2 и SLI-3 на месте;
3. `scripts/chaos.sh errors 0 && scripts/chaos.sh latency 800ms 1` — падает
   SLI-2 скорости при живой доступности. 800 мс, а не 300: порог мягкий,
   деградация должна пробивать его гарантированно;
4. `kubectl scale deploy/worker -n sentinel --replicas=0` — падает только
   SLI-3, конвейер встал, API здоров. На панели шагов пробера — ни одного
   отказа: видно, что индикаторы независимы;
5. `kubectl scale deploy/api -n sentinel --replicas=0` — все шаги пробера
   красные, «хорошие минуты» уходят в ноль, а RBSLO показывает «нет данных»:
   запросов нет вовсе. Это и есть слепая зона request-based подхода,
   которую закрывает пробер — говорится вслух;
6. откат: `kubectl scale ... --replicas=2`, `scripts/chaos.sh off` —
   восстановление всех графиков и остановка выгорания бюджета.

Проверено: `go test ./...` — ok (5 тестов middleware и 4 теста конфигурации
новые), `go build`, `gofmt`, `docker compose config` — чисто; `bash -n`
по обоим скриптам — ошибок нет. Сами скрипты против живого окружения
не прогонялись: ни compose, ни minikube не поднят.

### Две правки после первого прогона на кластере

Первый прогон демонстрации ничего не показал на графиках. Нашлись две причины,
обе исправлены.

1. **Внесённый сбой не попадал в SLI доступности.** Chaos-middleware обрывает
   запрос до того, как chi определит маршрут, поэтому метрика записывала его
   с меткой `route="unmatched"` — а она из SLI доступности исключена.
   Теперь middleware перед обрывом сам сопоставляет путь с деревом маршрутов
   (`chi.Routes.Match`) и проставляет шаблон в контекст
   (`internal/transport/http/middleware/chaos.go`, тест
   `TestChaos_KeepsRoutePatternOnInjectedError`). Проверено на кластере: 503
   пишутся с маршрутами `/api/v1/auth/login`, `/api/v1/monitors`,
   `/api/v1/public/status/{slug}`.
2. **SLI конвейера показывал разрыв вместо нуля.** При остановленном воркере
   рядов `sentinel_probes_total` нет вовсе, пустой результат не превращается
   в ноль. Добавлено `or vector(0)` в правило `sentinel:sli:ratio5m{slo="pipeline"}`
   (`k8s/monitoring/sli-rules.yaml`). Проверено: при `--replicas=0` индикатор
   уходит в 0.

Отдельно — операционная ловушка, из-за которой нагрузка пропадала:
`scripts/chaos.sh` делает `kubectl set env`, то есть перекатывает поды api,
и `kubectl port-forward` вместе с `scripts/slo-load.sh` на хосте умирают.
В `Команды-ДЗ5.md` шаг 6 переписан: нагрузку надёжнее брать изнутри кластера,
участив пробер.

### Третья правка: пустой гейдж сводного SLA

Панель «Сводный SLA, 30 дней» ничего не показывала, и вместе с ней пустовал
остаток бюджета ошибок. Правила при этом были `health: ok`, но у производных
стояло `lastSamples: 0` при `lastSeriesFetched: 3` — ряды Victoria Metrics
знала, а свежих точек не отдавала.

Причина в интервале группы `sentinel-slo`: он был 5m. Производные правила
(`error_budget_remaining`, `sla_compound`, `burn_rate:ratio6h`) считаются не
из сырых метрик, а из записанных рядов `ratio30d` и `ratio6h`. Запись идёт
через remote write асинхронно, поэтому в том же цикле её ещё не видно,
а к следующему циклу последняя точка оказывается ровно на границе окна
беспамятства Victoria Metrics (те же 5 минут) и в выборку не попадает.

Интервал группы снижен до 1m. Запрос по 30-дневному окну дорогой, но на этом
объёме данных он выполняется за 30 мс, так что цена приемлема.
