# Sentinel — мониторинг доступности и статус-страница

Сервис следит за доступностью веб-ресурсов: по расписанию опрашивает заданные
URL, хранит историю проверок, сам определяет момент падения и восстановления,
ведёт журнал инцидентов и публикует статус-страницу.

Сделано как клиент-серверное приложение по методологии [12 factors](https://12factor.net/ru/):
подробное обоснование по каждому фактору — в [Отчёт.md](%D0%9E%D1%82%D1%87%D1%91%D1%82.md).

Как устроен проект изнутри — слои, путь запроса, работа воркера, инварианты БД,
отладка — в [docs/Разбор.md](docs/%D0%A0%D0%B0%D0%B7%D0%B1%D0%BE%D1%80.md).

## Быстрый старт

Нужен только Docker с Compose.

```bash
cp .env.example .env
docker compose up --build -d
```

Или через Makefile:

```bash
make up
```

Доступно после запуска:

| Адрес | Что это |
|---|---|
| http://localhost:8080 | веб-интерфейс (nginx + статика) |
| http://localhost:8081 | API напрямую |
| http://localhost:8081/healthz | жив ли процесс |
| http://localhost:8081/readyz | готов ли принимать трафик (проверяет БД) |

Наполнить демо-данными и получить ссылку на публичную статус-страницу:

```bash
make demo
```

Сквозная проверка всего контракта на поднятом окружении:

```bash
bash scripts/smoke.sh http://localhost:8081
```

Остановить и удалить данные:

```bash
make down
```

## Доменная область

| Сущность | Смысл |
|---|---|
| **User** | владелец мониторов; у каждого есть непредсказуемый слаг публичной статус-страницы |
| **Monitor** | наблюдаемая цель: URL, метод, интервал, таймаут, ожидаемый код, порог падений |
| **Check** | результат одной проверки: успех, код ответа, задержка, текст ошибки |
| **Incident** | непрерывный период недоступности монитора: начало, конец, причина |

CRUD в задании — это операции над `Monitor`; `Check` и `Incident` порождает
воркер, а наружу они отдаются выборками и агрегатами.

### Как работает определение падения

Одиночная сетевая ошибка не должна поднимать тревогу, поэтому инцидент
открывается только когда подряд провалилось `failure_threshold` проверок.
Решение принимает чистая функция `domain.EvaluateProbe`: она получает текущее
состояние монитора и результат проверки и возвращает переход — новый статус,
счётчик падений и признаки «открыть инцидент» / «закрыть инцидент».
Воркер применяет этот переход одной транзакцией. Логика состояний не размазана
по инфраструктуре и покрыта юнит-тестами без БД и без сети.

## Стек

- **Go 1.24** — `chi` (роутер), `pgx/v5` (драйвер и пул), `golang-jwt`, `caarlos0/env` + `go-playground/validator` (конфигурация), `slog` (логи), `errgroup` (пул проверок)
- **PostgreSQL 17** — единственное хранилище; миграции `golang-migrate`
- **Фронтенд** — HTML, CSS и нативный JavaScript без сборки; раздаётся nginx, который же проксирует `/api`
- **Окружение** — Docker, Docker Compose
- **Тесты** — `testify`, `testcontainers-go` для интеграционных
- **Качество** — `golangci-lint`, GitHub Actions

Стек выбран намеренно нетяжёлым: нет Node в образах, нет брокера и кэша —
окружение поднимается на ноутбуке и не помешает следующим заданиям курса.

## Архитектура

Чистая архитектура, зависимости направлены строго внутрь:

```
cmd/api  cmd/worker  cmd/cleanup      точки входа: конфиг, логгер, запуск
        │
        ▼
internal/app                          composition root: ручная сборка, lifecycle
        │
        ├────────────────┬──────────────────┐
        ▼                ▼                  ▼
internal/transport   internal/worker   (одноразовые процессы)
  HTTP: роутер,        планировщик и
  middleware,          пул проверок
  handlers, mapper
        │                │
        ▼                ▼
internal/usecase                      по пакету на сценарий; порты объявлены
  Execute(ctx, req)                   локально рядом с потребителем
        │
        ├──────────────────────────────┐
        ▼                              ▼
internal/domain                   internal/infra
  сущности, sentinel-ошибки,        репозитории PostgreSQL, prober,
  переходы состояний                 хеширование паролей, JWT
  (ноль внешних зависимостей)
```

Правила, которые соблюдаются:

- `domain` не знает ни про HTTP, ни про SQL — в нём нет ни одного импорта
  фреймворка или драйвера;
- порт объявляет тот, кто его использует: интерфейс `MonitorRepo` живёт в пакете
  usecase и содержит только нужные ему методы, а реализует его `infra`;
- хендлеры вызывают только usecase, никогда не репозитории;
- доменные структуры наружу не отдаются — между ними и JSON стоит `mapper`;
- сборка зависимостей ручная, в `internal/app`, без DI-контейнера;
- миграции — отдельный шаг запуска, а не часть старта приложения.

### Три процесса из одной кодовой базы

| Процесс | Назначение | Масштабирование |
|---|---|---|
| `api` | HTTP API, stateless | сколько угодно экземпляров за балансировщиком |
| `worker` | опрос целей по расписанию | сколько угодно: мониторы разбираются через `FOR UPDATE SKIP LOCKED` |
| `cleanup` | одноразовая очистка истории проверок | запускается вручную или по расписанию |

Проверить, что воркеры действительно не мешают друг другу:

```bash
make up-scaled   # три воркера одновременно
```

## Безопасность

Сервис по заданию пользователя ходит на произвольный URL, то есть сам по себе
является инструментом **SSRF**: без фильтрации любой зарегистрировавшийся мог бы
просканировать внутреннюю сеть или прочитать облачные метаданные
(`169.254.169.254`). Поэтому:

- адрес проверяется дважды — при разборе URL и в момент установки соединения
  хуком `Control` у диалера, что закрывает и DNS rebinding, и редирект
  на внутренний адрес;
- запрещены приватные, loopback, link-local, CGNAT и multicast сети
  (`internal/infra/prober/guard.go`), каждый редирект проверяется заново;
- разрешены только схемы `http`/`https`, только безопасные методы
  (`GET`, `HEAD`, `OPTIONS`), учётные данные в URL отклоняются;
- тело ответа вычитывается с ограничением (`WORKER_MAX_RESPONSE_BYTES`),
  чтобы цель не могла исчерпать память воркера.

Остальное:

- пароли — `bcrypt`, стоимость из конфигурации; хеш не входит в DTO
  по построению, его просто нет в структуре ответа;
- доступ к API — JWT HS256; процесс `api` не хранит сессий и остаётся stateless;
- чужой монитор возвращает `404`, а не `403` — чтобы не раскрывать факт
  существования чужих ресурсов;
- вход неизвестным email и вход с неверным паролем дают одинаковый ответ,
  иначе перебором можно выяснить, какие адреса зарегистрированы;
- публичная статус-страница не отдаёт URL целей — только имена сервисов;
  доступ к ней даёт знание слага с ~80 битами энтропии;
- в production запрещены значение секрета из `.env.example`
  и `WORKER_ALLOW_PRIVATE_TARGETS=true` — проверяется на старте;
- контейнеры работают не от root.

## API

Полный контракт — [api/openapi/sentinel.yaml](api/openapi/sentinel.yaml).

```
POST   /api/v1/auth/register              регистрация, сразу выдаёт токен
POST   /api/v1/auth/login                 вход
GET    /api/v1/me                         текущий пользователь и слаг статус-страницы

GET    /api/v1/monitors                   список (limit, offset)
POST   /api/v1/monitors                   создать
GET    /api/v1/monitors/{id}              прочитать
PATCH  /api/v1/monitors/{id}              изменить частично
DELETE /api/v1/monitors/{id}              удалить

GET    /api/v1/monitors/{id}/checks       проверки за период
GET    /api/v1/monitors/{id}/stats        аптайм, средняя задержка, p95, корзины графика
GET    /api/v1/monitors/{id}/incidents    история инцидентов

GET    /api/v1/public/status/{slug}       публичная статус-страница, без токена

GET    /healthz                           процесс жив
GET    /readyz                            готов принимать трафик
```

Ошибки всегда имеют вид `{"code": "MONITOR_NOT_FOUND", "description": "..."}`:
клиент принимает решения по `code`, а не по тексту.

Пример:

```bash
TOKEN=$(curl -sS -X POST http://localhost:8081/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"me@example.com","password":"password123"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

curl -sS -X POST http://localhost:8081/api/v1/monitors \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Example","target":"https://example.com","interval_seconds":30,"timeout_seconds":5,"is_public":true}'
```

## Конфигурация

Вся конфигурация — переменные окружения, полный список с комментариями
в [.env.example](.env.example). Значений по умолчанию нет у двух переменных,
и это осознанно: `DATABASE_URL` и `AUTH_JWT_SECRET` обязательны, потому что
приложение не должно «знать» свою базу и свой секрет из кода.

Конфигурация валидируется на старте дважды: тегами (`required`, диапазоны,
`oneof`) и кросс-полевыми проверками — например, пул соединений не может быть
меньше параллелизма воркера, а в production нельзя оставить пример секрета.
Неверная конфигурация роняет процесс сразу, а не через час работы.

## Разработка

```bash
make test              # юнит-тесты, Docker не нужен
make test-race         # то же с детектором гонок
make test-integration  # репозитории против настоящей PostgreSQL (testcontainers)
                       # нужен Docker; если образ postgres ещё не скачан:
                       # docker pull postgres:17-alpine
make lint              # golangci-lint
make build             # бинарники в ./bin
```

Запуск процессов локально, без контейнеров (БД поднята отдельно):

```bash
export $(grep -v '^#' .env | xargs)
go run ./cmd/api
go run ./cmd/worker
```

Тесты разделены на три уровня:

- **юнит** — рядом с кодом, без БД и сети; покрывают переходы состояний,
  валидацию, защиту целей, конфигурацию;
- **интеграционные** — `internal/integrationtests`, билд-тег `integration`,
  поднимают PostgreSQL через testcontainers и накатывают те же миграции,
  что в проде; проверяют SQL, ограничения БД и выдачу мониторов нескольким
  воркерам одновременно;
- **сквозная проверка** — `scripts/smoke.sh`, работает с поднятым окружением
  только через HTTP, как чёрный ящик.

## Структура

```
api/openapi/           контракт API
cmd/{api,worker,cleanup}  точки входа трёх процессов
docker-compose.yaml    полное окружение: postgres, миграции, api, worker, web
deployments/           Dockerfile процессов, Dockerfile фронтенда, конфиг nginx
internal/
  app/                 composition root
  config/              конфигурация из env
  domain/              сущности, ошибки, переходы состояний
  infra/
    auth/              bcrypt, JWT
    db/postgres/       пул, транзакции, миграции, репозитории
    prober/            HTTP-проверки и защита от SSRF
  transport/http/      роутер, middleware, хендлеры, DTO, mapper
  usecase/             по пакету на сценарий
  worker/              планировщик и пул проверок
  integrationtests/    тесты против настоящей БД
scripts/               demo.sh, smoke.sh
web/                   фронтенд без сборки
```

## Что дальше

Задел, под который уже подготовлена структура:

- `monitor_kind` в схеме — enum с запасом: `tls_cert` (срок и параметры
  сертификата) и `tcp_port` добавляются новым prober'ом за тем же портом
  `worker.Prober`, без миграции схемы и без изменения контракта API;
- таблица `checks` неизменяема и читается только агрегатами — она переносится
  в колоночную БД заменой реализации порта `CheckRepo`, объявленного в usecase;
- алерты в Telegram — ещё один потребитель перехода состояний, который уже
  возвращает `recordprobe.Usecase`.
