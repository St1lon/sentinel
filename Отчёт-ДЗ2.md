# Отчёт по ДЗ 2: развёртывание в Kubernetes

## Замечания по ДЗ 1 учел и исправил

- **Пароль БД больше не имеет значения по умолчанию.** В `docker-compose.yaml`
  переменная `POSTGRES_PASSWORD` объявлена обязательной (`${POSTGRES_PASSWORD:?...}`)
- **Теги базовых образов зафиксированы до патч-версии:** `golang:1.24.13-alpine3.23`,
  `alpine:3.23.3`, `postgres:17.11-alpine`.
- **nginx работает от непривилегированного пользователя.** Перешёл на образ
  `nginxinc/nginx-unprivileged:1.27.5-alpine`

**Приложение:** Sentinel — сервис мониторинга доступности веб-ресурсов
с публичной статус-страницей. Состоит из трёх постоянных процессов
(`api`, `worker`, `web`), разового процесса миграций, периодической задачи
очистки и PostgreSQL.

Развёрнуто в minikube (драйвер docker, рантайм containerd).

## 1. Использованные абстракции Kubernetes

| Абстракция | Файл | Назначение |
|---|---|---|
| **Namespace** | `00-namespace.yaml` | namespace `sentinel`, изоляция объектов приложения |
| **ConfigMap** | `01-configmap.yaml` | несекретная конфигурация, подключается через `envFrom` |
| **ConfigMap** | `20-migrations-configmap.yaml` | SQL-файлы миграций, монтируется томом в `/migrations` |
| **Secret** | `02-secret.yaml` | пароль БД, ключ подписи JWT, строка подключения |
| **StatefulSet** | `10-postgres.yaml` | PostgreSQL, 1 реплика, стабильное имя пода `postgres-0` |
| **PersistentVolumeClaim** | `10-postgres.yaml` | том 1 ГиБ через `volumeClaimTemplates`, переживает перезапуск пода |
| **Deployment** | `30-api.yaml` | `api`, 2 реплики, HTTP API |
| **Deployment** | `40-worker.yaml` | `worker`, 1 реплика, опрос целей по расписанию |
| **Deployment** | `50-web.yaml` | `web`, 1 реплика, nginx: статика и прокси `/api` |
| **Service** (headless) | `10-postgres.yaml` | `postgres`, `clusterIP: None` |
| **Service** (ClusterIP) | `30-api.yaml` | `api:8080`, балансировка между репликами |
| **Service** (NodePort) | `50-web.yaml` | `web`, порт 30080, вход снаружи кластера |
| **Job** | `21-migrate-job.yaml` | накат миграций до старта приложения |
| **CronJob** | `60-cleanup-cronjob.yaml` | очистка истории проверок, ежечасно |
| **initContainer** | `21-`, `30-`, `40-` | ожидание готовности БД и применённой схемы |
| **Probes** | `10-`, `30-`, `50-` | `livenessProbe` и `readinessProbe` |
| **Resources** | все Deployment и StatefulSet | `requests` и `limits` по CPU и памяти |

Дополнительно по некоторым объектам:

- `api`, `worker`, `web` масштабируются горизонтально: `kubectl scale deployment/<имя> --replicas=N -n sentinel`;
- стратегия обновления Deployment — `RollingUpdate` с `maxUnavailable: 0`;
- `readinessProbe` у `api` обращается к `/readyz` (проверяет БД), `livenessProbe` — к `/healthz` (БД не трогает);
- у `postgres` обе пробы через `exec` с `pg_isready`;
- init-контейнеры заменяют `depends_on` из docker compose, которого в Kubernetes нет.

## 2. Взаимодействие сервисов

Связь построена на встроенном DNS кластера (CoreDNS): каждому Service
создаётся запись `<имя-сервиса>.<namespace>.svc.cluster.local`, внутри одного
namespace достаточно короткого имени. Поэтому в конфигурации нет ни одного
IP-адреса — адреса задаются именами сервисов.

| Откуда | Куда | Как |
|---|---|---|
| браузер | `web` | NodePort 30080 на ноде |
| `web` (nginx) | `api` | `proxy_pass http://api:8080` для запросов с префиксом `/api/` |
| `api` | `postgres` | строка подключения из Secret, хост `postgres:5432` |
| `worker` | `postgres` | то же подключение |
| `worker` | внешние цели | исходящие HTTP-запросы за пределы кластера |
| `migrate` (Job) | `postgres` | накат миграций из примонтированного ConfigMap |
| `cleanup` (CronJob) | `postgres` | удаление устаревших проверок |

Отдельно стоит отметить: **`worker` и `api` между собой не взаимодействуют**.
Их связывает только база — воркер забирает из неё мониторы, которым пора
проверяться, и пишет туда результаты, а `api` эти результаты читает. Поэтому
воркеры масштабируются независимо: координатор не нужен, мониторы разбираются
запросом с `FOR UPDATE SKIP LOCKED`, и одна цель не достаётся двум воркерам.

Статика фронтенда и API доступны по одному адресу (nginx отдаёт файлы сам и
проксирует `/api`), поэтому браузер работает с одним origin и CORS в обычной
работе не задействован.

### Источники конфигурации

Адреса и параметры не зашиты в образы, а приходят в поды переменными окружения:

| Источник | Что даёт | Как подключается |
|---|---|---|
| ConfigMap `sentinel-config` | настройки приложения | `envFrom`, весь блок |
| Secret `sentinel-secrets` | `DATABASE_URL`, `AUTH_JWT_SECRET`, пароль БД | `secretKeyRef`, поштучно |
| ConfigMap `sentinel-migrations` | SQL-файлы миграций | том в `/migrations` |

Один и тот же образ работает и в docker compose, и в minikube — меняются
только значения в ConfigMap и Secret.
