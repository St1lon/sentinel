# Отчёт по домашнему заданию №1

**Приложение:** Sentinel — сервис мониторинга доступности веб-ресурсов
с публичной статус-страницей.

---

## 1. Доменная область

Приложение решает задачу, с которой сталкивается любой владелец сайта или API:
**узнать о недоступности раньше, чем о ней сообщат пользователи**, и иметь
объективные данные о том, насколько часто и насколько долго сервис был недоступен.

Что происходит с точки зрения пользователя:

1. Пользователь регистрируется и добавляет **монитор** — указывает URL, как часто
   его проверять, сколько ждать ответа и какой код ответа считать нормальным.
2. Сервис начинает периодически опрашивать эту цель и сохранять **результат
   каждой проверки**: успех или неудача, код ответа, задержка, текст ошибки.
3. Когда проверки начинают падать, сервис сам решает, что цель действительно
   недоступна, и открывает **инцидент**. Когда цель отвечает снова — закрывает его.
4. Пользователь видит в панели управления текущий статус, аптайм за период,
   среднюю задержку и p95, график по часам, историю инцидентов и журнал проверок.
5. Выбранные мониторы можно опубликовать на **статус-странице** — публичной
   ссылке, которую можно дать своим пользователям.

Содержательная часть домена — не CRUD, а **определение момента падения**.
Одиночная сетевая ошибка не должна поднимать тревогу, иначе система превращается
в генератор ложных срабатываний. Поэтому у монитора есть порог
`failure_threshold`: инцидент открывается только когда подряд провалилось
заданное число проверок. Это решение принимает чистая функция
`domain.EvaluateProbe` ([internal/domain/transition.go](internal/domain/transition.go)):
она получает текущее состояние монитора и результат проверки и возвращает
переход — новый статус, счётчик падений, признаки «открыть инцидент»
и «закрыть инцидент». Воркер применяет этот переход одной транзакцией.

Отдельная особенность домена, влияющая на архитектуру: **результаты проверок
растут линейно по времени и читаются только агрегатами**. Сто мониторов
с интервалом 30 секунд дают около 288 тысяч записей в сутки. Поэтому таблица
`checks` сделана неизменяемой (только `INSERT` и чтение агрегатами), а все
выборки для графиков — свёртки на стороне БД (`date_trunc`,
`percentile_disc`, `count(*) FILTER (WHERE up)`), а не вытягивание строк
в приложение.

## 2. Стек реализации

| Слой | Технология | Почему именно так |
|---|---|---|
| Язык | Go 1.24 | статическая сборка, низкое потребление памяти, нативная конкурентность для пула проверок |
| HTTP | `go-chi/chi` v5 | минимальный роутер поверх `net/http`, без своего рантайма и своих абстракций |
| БД | PostgreSQL 17 | транзакции, `FOR UPDATE SKIP LOCKED` для распределения работы между воркерами, частичные и уникальные индексы, оконные агрегаты |
| Драйвер | `jackc/pgx` v5 + `pgxpool` | сырой SQL без ORM, прямой доступ к типам PostgreSQL и к коду ошибки |
| Миграции | `golang-migrate` | обратимые миграции, запускаются отдельным шагом |
| Конфигурация | `caarlos0/env` + `go-playground/validator` | чтение env по struct-тегам и валидация на старте |
| Аутентификация | `golang-jwt/jwt` v5 (HS256), `bcrypt` | stateless-токены, чтобы процесс api не хранил сессий |
| Логи | стандартный `log/slog` | структурированный JSON в stdout, без внешних зависимостей |
| Конкурентность | `golang.org/x/sync/errgroup` | пул проверок с ограничением параллелизма |
| Фронтенд | HTML + CSS + нативный JavaScript | без сборки и без `node_modules`: окружение остаётся лёгким |
| Раздача фронтенда | nginx | статика плюс прокси `/api` — браузер работает с одним origin |
| Окружение | Docker + Docker Compose | одинаковый способ запуска локально и в CI |
| Тесты | `testify`, `testcontainers-go` | юнит-тесты без инфраструктуры, интеграционные — против настоящей БД |
| Качество | `golangci-lint`, GitHub Actions | единый набор правил, прогон в CI |

Стек выбран намеренно нетяжёлым, как советует задание: один язык на бэкенде,
одна СУБД, никакого брокера, кэша и сборщика фронтенда. Всё окружение
поднимается одной командой и не мешает последующим заданиям курса.

### Архитектура кода

Чистая архитектура, зависимости направлены строго внутрь:

- `internal/domain` — сущности, sentinel-ошибки и переходы состояний.
  Ноль импортов фреймворков, драйверов, SQL и HTTP.
- `internal/usecase` — по пакету на сценарий, единственный публичный метод
  `Execute(ctx, req)`. Порты (интерфейсы репозиториев и внешних клиентов)
  объявлены **локально рядом с потребителем** и содержат только нужные ему методы.
- `internal/infra` — реализации портов: репозитории PostgreSQL, HTTP-prober,
  bcrypt, JWT.
- `internal/transport/http` — роутер, middleware, хендлеры, DTO и mapper.
  Доменные структуры наружу не отдаются никогда.
- `internal/worker` — планировщик и пул проверок: только оркестрация,
  бизнес-правила остаются в домене.
- `internal/app` — composition root: ручная сборка зависимостей без
  DI-контейнера, управление жизненным циклом.
- `cmd/{api,worker,cleanup}` — точки входа: конфиг, логгер, запуск.

## 3. Основные сущности

### User — пользователь

| Поле | Назначение |
|---|---|
| `id` | UUID |
| `email` | уникальный, нормализуется к нижнему регистру |
| `password_hash` | bcrypt; в DTO ответа отсутствует по построению |
| `status_page_slug` | непредсказуемый идентификатор публичной статус-страницы (~80 бит энтропии) |
| `created_at` | момент регистрации |

### Monitor — наблюдаемая цель

| Поле | Назначение |
|---|---|
| `id`, `user_id` | идентификатор и владелец |
| `name` | имя, уникальное в пределах пользователя |
| `kind` | вид проверки: `http`, `tls_cert`, `tcp_port` (реализован `http`) |
| `target` | URL цели |
| `method` | `GET`, `HEAD` или `OPTIONS` — только безопасные и идемпотентные |
| `interval_seconds` | период проверки, 10…86400 |
| `timeout_seconds` | таймаут, 1…120, строго меньше интервала |
| `expected_status` | код ответа, считающийся нормальным |
| `failure_threshold` | сколько подряд падений открывает инцидент, 1…10 |
| `is_public` | показывать ли на публичной статус-странице |
| `paused` | приостановлен ли мониторинг |
| `status` | `pending` / `up` / `down` / `paused` — вычисляется воркером |
| `consecutive_failures` | текущая серия падений |
| `last_checked_at`, `next_check_at` | когда проверяли и когда проверить снова |

**Над этой сущностью реализован полный CRUD** — он же будет основой
для последующих заданий.

### Check — результат одной проверки

| Поле | Назначение |
|---|---|
| `id`, `monitor_id` | идентификатор и монитор |
| `checked_at` | момент проверки |
| `up` | успешна ли проверка |
| `status_code` | код ответа, если ответ получен |
| `latency_ms` | задержка |
| `error` | текст ошибки, если была |

Записи неизменяемы: только `INSERT` и чтение агрегатами.

### Incident — период недоступности

| Поле | Назначение |
|---|---|
| `id`, `monitor_id` | идентификатор и монитор |
| `started_at`, `resolved_at` | начало и конец; `NULL` в `resolved_at` — инцидент открыт |
| `cause` | причина: текст сетевой ошибки или несовпадение кода ответа |

Инвариант «не больше одного открытого инцидента на монитор» обеспечен
**частичным уникальным индексом в БД**
(`CREATE UNIQUE INDEX ... ON incidents (monitor_id) WHERE resolved_at IS NULL`),
а не только кодом: при гонке двух воркеров вторая вставка просто не пройдёт.

### Связи

```
User 1 ──── N Monitor 1 ──── N Check
                      1 ──── N Incident
```

Удаление пользователя каскадно удаляет мониторы, удаление монитора — его
проверки и инциденты (`ON DELETE CASCADE`).

## 4. Соответствие методологии 12 факторов

### I. Кодовая база (Codebase)

Одна кодовая база под контролем версий, из которой разворачиваются все деплои.
Три процесса — `api`, `worker` и `cleanup` — это три точки входа
(`cmd/api`, `cmd/worker`, `cmd/cleanup`) **одного** Go-модуля; они делят
домен, конфигурацию и репозитории. Разные окружения (локальное, CI, прод)
различаются только значениями переменных окружения, а не кодом и не ветками.

Один образ собирается из одного `deployments/Dockerfile`, процесс выбирается
аргументом сборки `SERVICE`, поэтому версии процессов не могут разойтись.

### II. Зависимости (Dependencies)

Зависимости объявлены явно и зафиксированы: `go.mod` с точными версиями
и `go.sum` с контрольными суммами. Ничего не берётся из системы: образ
собирается с `CGO_ENABLED=0`, бинарник статический, в рантайм-образ
доустанавливаются только `ca-certificates` (нужны для проверки HTTPS-целей)
и `tzdata`.

Фронтенду вообще нечего объявлять: это HTML, CSS и нативный JavaScript,
без сборщика и без `node_modules`. Утилиты, не нужные приложению в рантайме
(`golangci-lint`, `migrate`), вызываются отдельно и не входят в образ.

В Dockerfile зависимости скачиваются отдельным слоем до копирования кода
(`COPY go.mod go.sum` → `go mod download` → `COPY . .`), поэтому правка кода
не инвалидирует кэш модулей.

### III. Конфигурация (Config)

Вся конфигурация читается из переменных окружения
([internal/config/config.go](internal/config/config.go)), по блоку на каждый
concern: `AppConfig`, `LogConfig`, `PostgresConfig`, `HTTPConfig`, `AuthConfig`,
`WorkerConfig`, `RetentionConfig`. В коде нет ни одного адреса, пароля или ключа.

Два значения **намеренно оставлены без дефолта** и обязательны:
`DATABASE_URL` и `AUTH_JWT_SECRET`. Приложение не должно «знать» свою базу
и свой секрет из кода — без них процесс не стартует.

Конфигурация валидируется на старте двухуровнево:

- тегами: `required`, диапазоны (`min`/`max`), перечисления
  (`oneof=development staging production`), минимальная длина секрета;
- кросс-полевыми проверками ([internal/config/checks.go](internal/config/checks.go)):
  `POSTGRES_MIN_CONNS` не больше `POSTGRES_MAX_CONNS`, пул соединений
  не меньше параллелизма воркера, в `production` запрещены значение секрета
  из `.env.example` и `WORKER_ALLOW_PRIVATE_TARGETS=true`.

Неверная конфигурация роняет процесс сразу, а не через час работы.
Файл `.env` в репозиторий не попадает (`.gitignore`), в репозитории лежит
только `.env.example` с комментариями.

### IV. Сторонние службы (Backing services)

PostgreSQL — присоединённый ресурс: единственное, что приложение о нём знает,
это строка подключения `DATABASE_URL` из окружения. Локальную БД из compose
можно заменить на управляемый кластер, не меняя ни строки кода.

Доступ к БД изолирован за портами, объявленными в пакетах usecase
(`MonitorRepo`, `CheckRepo`, `IncidentRepo`, `UserRepo`). Поэтому заменить
хранилище можно, добавив новую реализацию порта и исправив только сборку
в `internal/app`.

Проверяемые цели мониторинга — тоже присоединённые ресурсы: prober спрятан
за портом `worker.Prober`, а его настройки (`User-Agent`, лимиты, число
редиректов) приходят из конфигурации, а не захардкожены в клиенте.

### V. Сборка, релиз, выполнение (Build, release, run)

Стадии разделены:

- **Сборка** — стадия `builder` в `deployments/Dockerfile`: компиляция
  с `-trimpath` и `-ldflags`, версия передаётся аргументом `VERSION`
  и попадает в `APP_VERSION`, который виден в `/healthz` и в каждой строке лога.
- **Релиз** — собранный образ плюс конфигурация окружения: образ неизменяем,
  переменные подставляются при запуске.
- **Выполнение** — запуск контейнера из готового образа; код внутри
  не собирается и не правится, рантайм-образ не содержит ни компилятора,
  ни исходников.

Откат — это запуск предыдущего образа с тем же окружением.
Миграции применяются отдельным шагом до старта приложения, а не из кода.

### VI. Процессы (Processes)

Процессы не хранят состояния и ничего не ждут друг от друга:

- аутентификация на JWT, серверных сессий нет, поэтому любой запрос может
  обслужить любой экземпляр `api`;
- на диск ничего не пишется, временные файлы не используются;
- расписание проверок живёт в БД (`next_check_at`), а не в памяти воркера:
  воркер можно убить в любой момент, никакое состояние не потеряется;
- кэшей в памяти процесса нет.

Всё разделяемое состояние — в PostgreSQL.

### VII. Привязка портов (Port binding)

Процесс `api` сам слушает TCP-порт из `HTTP_PORT` и экспортирует HTTP
([internal/transport/http/server.go](internal/transport/http/server.go)).
Это самодостаточный сервис: он не разворачивается внутрь контейнера приложений,
не требует внешнего веб-сервера и не зависит от модулей вроде mod_php.

nginx в compose стоит перед ним как обратный прокси и раздатчик статики,
но для работы API не обязателен — API доступен напрямую. Именно это свойство
позволит в следующем задании поставить перед несколькими экземплярами `api`
балансировщик, ничего не меняя в приложении.

### VIII. Параллелизм (Concurrency)

Масштабирование — процессами, а не потоками внутри одного процесса:

- **api** stateless, поэтому экземпляров может быть сколько угодно
  за балансировщиком;
- **worker** масштабируется горизонтально без координатора и без выбора
  лидера. Мониторы выдаются запросом с `FOR UPDATE SKIP LOCKED`, который
  в том же выражении сдвигает `next_check_at`
  ([internal/infra/db/postgres/repository/monitor.go](internal/infra/db/postgres/repository/monitor.go)):
  один монитор физически не может достаться двум воркерам. Проверить:
  `make up-scaled` поднимает три воркера, а интеграционный тест
  `TestMonitorRepo_LeaseDueGivesEachMonitorToSingleWorker` запускает их
  имитацию в несколько горутин и убеждается, что выдача не пересекается.

Внутри воркера параллелизм ограничен явно (`errgroup.SetLimit`,
`WORKER_CONCURRENCY`), а конфигурация не даёт задать параллелизм больше пула
соединений к БД.

### IX. Утилизируемость (Disposability)

Процессы быстро стартуют и корректно останавливаются:

- запуск занимает доли секунды: это один статический бинарник, которому нужно
  лишь прочитать env и открыть пул соединений;
- `SIGTERM` и `SIGINT` перехватываются через `signal.NotifyContext`
  (`cmd/*/main.go`), после чего HTTP-сервер прекращает принимать новые
  соединения и даёт активным запросам завершиться в пределах
  `HTTP_SHUTDOWN_TIMEOUT`, затем закрывается пул соединений;
- воркер выходит из цикла по отмене контекста;
- работа воркера идемпотентна по последствиям: аварийное завершение посреди
  цикла не портит данные, потому что запись проверки, смена статуса и операции
  с инцидентом идут **одной транзакцией**
  ([internal/usecase/probe/record/usecase.go](internal/usecase/probe/record/usecase.go));
  непроверенный монитор просто будет взят снова, когда наступит его время;
- ошибка одного цикла проверок не роняет процесс — она логируется, следующий
  тик пробует снова.

### X. Паритет разработки и работы (Dev/prod parity)

- Локально, в CI и в проде поднимается **один и тот же** `docker-compose.yaml`
  и один и тот же образ PostgreSQL (`postgres:17-alpine`) — не SQLite локально
  и PostgreSQL в проде.
- Схема во всех окружениях создаётся **одними и теми же миграциями**,
  включая интеграционные тесты: `internal/integrationtests` накатывает
  те же файлы `migrations/*.sql` на контейнер PostgreSQL через
  `golang-migrate`, поэтому тесты не могут проверять структуру, которой
  в проде нет.
- Различаются только значения env: уровень логов, стоимость bcrypt, размеры
  пулов, разрешение приватных целей для локальных экспериментов.
- CI прогоняет на том же образе окружение целиком (`compose-smoke`) и сквозной
  сценарий через HTTP, то есть проверяется ровно то, что будет запущено.
- Разрыв во времени минимален: любой коммит проходит lint, тесты, сборку
  образов и проверку окружения в одном прогоне.

### XI. Логи (Logs)

Логи — поток событий, а не файлы. Всё пишется структурированным JSON
в stdout через `log/slog` ([internal/app/logger.go](internal/app/logger.go));
приложение не открывает файлов, не ротирует их и ничего никуда не отправляет
само. Маршрутизацией занимается среда исполнения: `docker compose logs`
локально, сборщик логов в кластере.

Каждая запись несёт версию и окружение; HTTP-логгер добавляет метод, путь,
статус, размер ответа, длительность, `request_id` и идентификатор
пользователя, если запрос аутентифицирован. Смены состояния мониторов
и открытие/закрытие инцидентов логируются отдельными событиями с причиной —
это и есть то, по чему потом строятся алерты. Уровень и формат
(`json`/`text` для удобства локальной разработки) задаются переменными
`LOG_LEVEL` и `LOG_FORMAT`.

### XII. Задачи администрирования (Admin processes)

Административные задачи — одноразовые процессы из той же кодовой базы,
того же образа и с тем же окружением:

- **миграции**: отдельный сервис `migrate` в compose, который должен успешно
  завершиться прежде, чем запустятся `api` и `worker`
  (`depends_on: condition: service_completed_successfully`). В код приложения
  прогон миграций не встроен намеренно: иначе несколько одновременно
  поднимающихся экземпляров начали бы менять схему наперегонки;
- **очистка истории проверок**: процесс `cmd/cleanup`
  (`docker compose run --rm cleanup` или `make cleanup`) удаляет записи старше
  `RETENTION_CHECK_DAYS` пачками, чтобы не держать долгую блокировку
  на большой таблице, и завершается. В кластере это обычный CronJob
  из того же образа;
- **демо-данные**: `scripts/demo.sh` работает через публичный HTTP API,
  а не через SQL. Поэтому демо-пользователь не попадает в схему БД и не может
  случайно оказаться в продовом окружении вместе с миграциями.

Отдельного «админского» кода, который живёт только на чьей-то машине и может
разойтись с приложением по версии, в проекте нет.

## 5. Что сделано сверх требований задания

Эти вещи не требовались, но добавлены как задел под последующие задания курса
и как часть нормального качества:

- **защита от SSRF** — сервис по заданию пользователя ходит на произвольный
  URL, то есть сам по себе является инструментом сканирования внутренней сети.
  Адрес проверяется дважды: при разборе URL и в момент установки соединения
  хуком `Control` у диалера, что закрывает DNS rebinding и редирект
  на внутренний адрес ([internal/infra/prober/guard.go](internal/infra/prober/guard.go));
- **`/healthz` и `/readyz`** — разделены осознанно: `/healthz` не трогает БД,
  чтобы её кратковременная недоступность не вызывала перезапуск контейнера,
  а `/readyz` проверяет БД и предназначен для балансировщика;
- **контракт OpenAPI** ([api/openapi/sentinel.yaml](api/openapi/sentinel.yaml))
  и единый формат ошибок `{code, description}`;
- **три уровня тестов**: юнит-тесты без инфраструктуры (переходы состояний,
  валидация, защита целей, конфигурация), интеграционные против настоящей
  PostgreSQL через testcontainers (SQL, ограничения БД, конкурентная выдача
  мониторов) и сквозная проверка контракта по HTTP (`scripts/smoke.sh`);
- **CI на GitHub Actions**: линтер, тесты с детектором гонок, интеграционные
  тесты, сборка образов всех трёх процессов и проверка поднятого окружения
  целиком;
- **ограничения целостности в БД, а не только в коде**: `CHECK` на диапазоны
  значений монитора, уникальность имени монитора в пределах пользователя,
  частичный уникальный индекс «не более одного открытого инцидента
  на монитор», каскадное удаление.

## 6. Как проверить

```bash
cp .env.example .env
docker compose up --build -d

# демо-данные и ссылка на публичную статус-страницу
bash scripts/demo.sh http://localhost:8081

# сквозная проверка всего контракта
bash scripts/smoke.sh http://localhost:8081
```

- веб-интерфейс — <http://localhost:8080>
- API — <http://localhost:8081>

Проверка горизонтального масштабирования воркеров (фактор VIII):

```bash
docker compose up -d --scale worker=3
```

Тесты:

```bash
make test-race         # юнит-тесты с детектором гонок, Docker не нужен
make test-integration  # против настоящей PostgreSQL в контейнере
make lint              # golangci-lint
```
