# Разбор проекта

Документ для того, чтобы разобраться в проекте, не читая код построчно.
Здесь: что где лежит, как устроены слои, как проходит запрос насквозь,
как работает воркер, какие есть инварианты и как добавлять новое.

---

## 1. Что это

Сервис мониторинга доступности. Пользователь добавляет URL, сервис по
расписанию его опрашивает, хранит историю проверок, сам определяет момент
падения и восстановления, ведёт журнал инцидентов и публикует статус-страницу.

Запуск:

```bash
cp .env.example .env
docker compose up --build -d
```

- фронтенд — <http://localhost:8080>
- API — <http://localhost:8081>

---

## 2. Что запускается

Один Go-модуль, из которого собирается **три разных бинарника**. Это не
микросервисы: домен, конфигурация и репозитории общие, различаются только
точки входа. В Dockerfile процесс выбирается аргументом сборки:

```dockerfile
RUN go build -o /out/app ./cmd/${SERVICE}
```

| Контейнер | Что делает | Порт | Жизненный цикл |
|---|---|---|---|
| `postgres` | хранит всё состояние | 5432 | постоянно |
| `migrate` | накатывает миграции и выходит | — | разово при старте |
| `api` | HTTP API | 8080 (наружу 8081) | постоянно |
| `worker` | опрашивает цели по расписанию | нет | постоянно |
| `web` | nginx: статика + прокси `/api` | 80 (наружу 8080) | постоянно |
| `cleanup` | удаляет старые проверки и выходит | — | по требованию |

`api` и `worker` стартуют только после успешного завершения `migrate` —
в compose это `condition: service_completed_successfully`.

## 4. Слои и правило зависимостей

Зависимости направлены строго внутрь, наружу — никогда:

```
transport ──┐
            ├──> usecase ──> domain
worker ─────┘        ↑
                     │ (интерфейсы)
                  infra  ──────────┘ реализует
```

Что это значит на практике:

- **domain** не импортирует ничего, кроме стандартной библиотеки. Ни SQL,
  ни HTTP, ни JSON-тегов на структурах. Поэтому правила можно тестировать
  без БД и без сети.
- **usecase** сам объявляет, что ему нужно от внешнего мира. Интерфейс
  `MonitorRepo` лежит **в пакете usecase**, а не в пакете репозитория,
  и содержит ровно те методы, которые нужны этому сценарию. Например,
  `monitor/create/ports.go` — это один метод `Create`, и всё.
- **infra** реализует эти интерфейсы. Знание о PostgreSQL дальше репозитория
  не уходит: код ошибки `23505` превращается в `domain.ErrMonitorNameTaken`
  прямо в репозитории.
- **transport** вызывает только usecase, никогда репозитории напрямую.
  Доменные структуры наружу не отдаются — между ними и JSON стоит `mapper`.

Каждый usecase устроен одинаково, поэтому читается без разбега:

```
usecase/monitor/create/
  usecase.go   структура Usecase + NewUsecase + единственный метод Execute
  request.go   структура Request + приватный метод validate()
  ports.go     интерфейсы, которые нужны этому usecase
```

`Execute` всегда начинается с `req.validate()`.

## 5. Сквозной путь: создание монитора

Полезно проследить один запрос целиком — остальные устроены так же.

**1. Браузер.** `web/app.js` отправляет:

```
POST /api/v1/monitors
Authorization: Bearer <jwt>
{"name":"API","target":"https://example.com","interval_seconds":60}
```

**2. nginx** (`deployments/nginx.conf`) видит префикс `/api/` и проксирует
запрос в контейнер `api`.

**3. Роутер** (`internal/transport/http/router.go`). Цепочка middleware:
RequestID → RealIP → Recoverer → CORS → логгер. Путь попадает в защищённую
группу, поэтому дополнительно отрабатывает `middleware.Auth`.

**4. Auth** (`middleware/auth.go`) берёт заголовок, проверяет подпись и срок
токена через `infra/auth/jwt.go` и кладёт `userID` в контекст запроса.
Любая проблема с токеном — сразу 401, дальше запрос не идёт.

**5. Хендлер** (`handlers/monitor.go`, метод `CreateMonitor`):
достаёт `userID` из контекста, декодирует тело с ограничением размера
и запретом неизвестных полей, собирает `createmonitor.Request` и вызывает
usecase. Больше он ничего не делает — ни SQL, ни бизнес-правил.

**6. Usecase** (`usecase/monitor/create/`):

- `request.go` → `validate()`: нормализует имя и URL, подставляет значения
  по умолчанию, проверяет диапазоны и то, что таймаут меньше интервала;
- `usecase.go` → `Execute`: генерирует UUID, ставит статус `pending`
  и `next_check_at = now` (чтобы первая проверка прошла сразу), вызывает
  `monitors.Create`.

**7. Репозиторий** (`infra/db/postgres/repository/monitor.go`) выполняет
`INSERT`. Если сработало ограничение уникальности имени — возвращает
`domain.ErrMonitorNameTaken` вместо ошибки драйвера.

**8. Обратно наверх.** Хендлер получает `*domain.Monitor`, прогоняет его
через `mapper.Monitor` → `dto.Monitor` и отдаёт 201.

**Если на любом шаге ошибка**, она идёт в `apierrors.From` — таблица,
которая переводит доменную ошибку в HTTP-статус и машинный код:

```json
{"code": "MONITOR_NAME_TAKEN", "description": "monitor name already taken"}
```

Неизвестная ошибка превращается в 500 с текстом `internal error`,
а подробности уходят в лог. Клиент принимает решения по `code`, не по тексту.

## 6. Как работает воркер

`internal/worker/worker.go` — цикл с тикером раз в секунду. На каждом тике:

### Шаг 1. Взять мониторы в работу

`usecase/probe/lease` → `MonitorRepo.LeaseDue`. Один SQL-запрос:

```sql
WITH due AS (
    SELECT id FROM monitors
    WHERE paused = FALSE AND next_check_at <= $1
    ORDER BY next_check_at
    LIMIT $2
    FOR UPDATE SKIP LOCKED
)
UPDATE monitors AS m
SET next_check_at = $1 + make_interval(secs => m.interval_seconds),
    updated_at = $1
FROM due WHERE m.id = due.id
RETURNING m.id, m.user_id, ...
```

Два важных момента:

- `FOR UPDATE SKIP LOCKED` — «заблокируй эти строки, а занятые кем-то другим
  пропусти». Второй воркер не ждёт и получает другие строки;
- `next_check_at` сдвигается **тем же запросом**. Монитор не достанется никому
  повторно до наступления следующего интервала.

Благодаря этому воркеров можно запускать сколько угодно без координатора
и без выбора лидера. Вся синхронизация — одна строчка SQL.

`RETURNING` обязан перечислять колонки с префиксом `m.`: в запросе участвуют
и таблица, и CTE, в обеих есть `id`, без префикса Postgres падает
с `column reference "id" is ambiguous`.

### Шаг 2. Опросить цели

`errgroup` с лимитом `WORKER_CONCURRENCY` (по умолчанию 8 одновременно).
Каждая цель уходит в `infra/prober/http.go`.

Проверка возвращает `*domain.Check` — результат, **не ошибку**. Недоступная
цель это нормальный исход: `Up: false` и текст причины. Ошибка возвращается
только если проверку нельзя выполнить в принципе (неподдерживаемый вид монитора).

### Шаг 3. Записать результат

`usecase/probe/record`. Сначала домен решает, что изменилось:

```go
transition := domain.EvaluateProbe(req.Monitor, req.Check)
```

`EvaluateProbe` (`domain/transition.go`) — чистая функция без побочных
эффектов. Правила:

- успех → счётчик падений обнуляется, статус `up`; если монитор был `down`,
  инцидент закрывается;
- неудача → счётчик +1; инцидент открывается только когда счётчик достиг
  `failure_threshold` (защита от флаппинга — одиночный сетевой сбой не должен
  поднимать тревогу);
- неудача при уже открытом инциденте ничего не открывает заново.

Затем всё записывается **одной транзакцией**: вставка проверки, обновление
статуса монитора, открытие или закрытие инцидента. Иначе падение процесса
между шагами оставило бы монитор в статусе `down` без инцидента.

## 7. Модель данных

```
User 1 ──── N Monitor 1 ──── N Check
                      1 ──── N Incident
```

| Таблица | Назначение | Характер нагрузки |
|---|---|---|
| `users` | владельцы | мало строк, редкие записи |
| `monitors` | настройки целей + текущее состояние | мало строк, частые UPDATE от воркера |
| `checks` | результат каждой проверки | только INSERT, читается агрегатами, растёт линейно |
| `incidents` | периоды недоступности | мало строк |

Инварианты держит сама БД, а не только код:

- `CHECK` на диапазоны: интервал 10…86400, таймаут 1…120 и строго меньше
  интервала, порог 1…10, ожидаемый код 100…599;
- `UNIQUE (user_id, name)` — имя монитора уникально в пределах пользователя;
- частичный уникальный индекс `incidents (monitor_id) WHERE resolved_at IS NULL`
  — **не больше одного открытого инцидента на монитор**. При гонке двух
  воркеров вторая вставка просто не пройдёт;
- частичный индекс `monitors (next_check_at) WHERE paused = FALSE` — под
  основной запрос воркера;
- `ON DELETE CASCADE` — удаление монитора забирает его проверки и инциденты.

Агрегаты считаются в БД, а не в приложении:

```sql
count(*) FILTER (WHERE up)                                  -- успешные проверки
percentile_disc(0.95) WITHIN GROUP (ORDER BY latency_ms)    -- p95
date_trunc('hour', checked_at)                              -- корзины графика
```

Размер корзины (`hour`/`day`) подставляется в текст запроса, поэтому он
проверяется по белому списку `domain.BucketSize` — произвольная строка туда
не попадёт.

## 8. Конфигурация

Всё из переменных окружения, полный список в `.env.example`.
Блок на каждый concern: `AppConfig`, `LogConfig`, `PostgresConfig`,
`HTTPConfig`, `AuthConfig`, `WorkerConfig`, `RetentionConfig`.

Две переменные **обязательны и не имеют значения по умолчанию** —
`DATABASE_URL` и `AUTH_JWT_SECRET`. Приложение не должно знать свою базу
и свой секрет из кода.

Валидация на старте двухуровневая:

- теги: `required`, диапазоны, `oneof=development staging production`;
- кросс-полевые проверки в `config/checks.go`: пул соединений не меньше
  параллелизма воркера, `POSTGRES_MIN_CONNS <= POSTGRES_MAX_CONNS`,
  в production запрещены пример секрета и `WORKER_ALLOW_PRIVATE_TARGETS=true`.

Неверная конфигурация роняет процесс сразу, а не через час работы.

## 9. Безопасность

**Фильтр адресов (SSRF).** Сервис по заданию пользователя ходит на произвольный
URL, то есть сам по себе является инструментом сканирования внутренней сети.
Три уровня в `infra/prober/`:

1. разбор URL: только `http`/`https`, только `GET`/`HEAD`/`OPTIONS`, без
   учётных данных в URL, литеральные IP сверяются со списком запрещённых сетей;
2. хук `Control` у диалера: проверяет **фактический** IP перед `connect`,
   что закрывает DNS rebinding (имя резолвится во внутренний адрес уже после
   проверки URL);
3. `CheckRedirect`: каждый редирект проверяется заново и их число ограничено.

Запрещены приватные, loopback, link-local (включая `169.254.169.254` —
облачные метаданные), CGNAT, multicast и их IPv6-аналоги.

**Остальное:**

- пароли — bcrypt; хеша нет в DTO ответа по построению, его просто нет в структуре;
- чужой монитор отдаёт 404, а не 403 — чтобы не раскрывать факт существования;
- вход несуществующим email и вход с неверным паролем дают одинаковый ответ;
- публичная статус-страница не отдаёт URL целей, только имена сервисов;
  доступ к ней даёт знание слага (~80 бит энтропии);
- тело ответа цели читается с ограничением, чтобы не исчерпать память воркера;
- контейнеры работают не от root, с `no-new-privileges`.

## 10. Фронтенд

Без сборки: HTML, CSS и нативный JavaScript, четыре файла в `web/`.

- `api.js` — обёртка над `fetch`: базовый путь, Bearer-токен из localStorage,
  разбор ошибок `{code, description}`;
- `app.js` — панель: аутентификация, CRUD над мониторами, детали монитора
  с графиком, автообновление раз в 15 секунд;
- `status.js` — публичная страница по слагу, без токена;
- `style.css` — тёмная и светлая темы.

Адрес API не прописан: запросы идут на `/api/v1/...`, то есть на тот же origin,
что и страница. Поэтому CORS в обычной работе не задействован.

График аптайма — SVG, который рисуется прямо из корзин, посчитанных базой.
Никаких библиотек.

## 11. Тесты

| Уровень | Где | Что проверяет | Нужен Docker |
|---|---|---|---|
| юнит | рядом с кодом | переходы состояний, валидация, фильтр адресов, конфигурация, маппинг ошибок | нет |
| интеграционные | `internal/integrationtests` | SQL, ограничения БД, транзакции, конкурентная выдача мониторов | да |
| сквозной | `scripts/smoke.sh` | весь контракт по HTTP, как чёрный ящик | да |

```bash
go test ./...                                              # юнит
go test -tags=integration ./internal/integrationtests/...  # интеграционные
bash scripts/smoke.sh http://localhost:8081                # сквозной
```

Интеграционные поднимают настоящий PostgreSQL через testcontainers и
накатывают **те же** миграции, что в проде. Моков внутренних слоёв там нет.

Моки для портов написаны руками (стабы в тестах) — интерфейсы узкие,
генератор дал бы больше кода, чем экономии.

## 12. Как добавить новое

**Новое поле у монитора:**
1. миграция `00002_*.up.sql` и `.down.sql`;
2. поле в `domain.Monitor`;
3. колонка в `monitorColumns` и в SQL репозитория;
4. поле в `dto` и в `mapper`;
5. валидация в `usecase/common/validate` и в `request.go` создания/обновления;
6. поле в OpenAPI-контракте.

**Новый эндпоинт:**
1. пакет в `usecase/` по шаблону (`usecase.go`, `request.go`, `ports.go`);
2. метод-хендлер в `transport/http/handlers/`;
3. маршрут в `router.go`;
4. сборка usecase в `app/api.go`;
5. описание в OpenAPI.

**Новый вид проверки** (например, срок TLS-сертификата):
1. `kind` уже есть в enum схемы — миграция не нужна;
2. разрешить его в `validate.MonitorKind` и в `MonitorKind.IsImplemented`;
3. новая реализация порта `worker.Prober`;
4. выбор prober'а по виду монитора в `app/worker.go`.

## 13. Отладка: куда смотреть

| Симптом | Где искать |
|---|---|
| монитор в статусе «Ожидает», 0 проверок | `docker compose logs worker` — ошибки цикла логируются раз в секунду |
| 500 на запросе | лог `api`: неизвестные ошибки пишутся с полным текстом и `request_id` |
| контейнер `api` не стартует | ошибка валидации конфига печатается в stderr и процесс выходит |
| миграции не применились | `docker compose logs migrate`, статус должен быть `Exited (0)` |
| фронтенд не видит API | проверить, что открыт порт 8080 (nginx), а не 8081 |
| монитор не проверяется | `paused = true`, либо `next_check_at` в будущем |

Полезные запросы к БД:

```bash
docker compose exec postgres psql -U sentinel -d sentinel

-- что сейчас с мониторами
SELECT name, status, consecutive_failures, last_checked_at, next_check_at FROM monitors;

-- последние проверки
SELECT checked_at, up, status_code, latency_ms, error
FROM checks ORDER BY checked_at DESC LIMIT 20;

-- открытые инциденты
SELECT * FROM incidents WHERE resolved_at IS NULL;
```

## 14. Что осознанно не сделано

- **нет кэша** — нагрузки пока нет, Redis добавил бы контейнер и сложность
  инвалидации без выгоды;
- **нет брокера** — воркер читает задания из БД, очередь избыточна
  на этом объёме;
- **нет генерации кода из OpenAPI** — контракт есть и поддерживается вручную;
  `oapi-codegen` имеет смысл, когда контракт меняется часто;
- **нет метрик и трейсинга** — следующий шаг, сервис для этого готов:
  Prometheus-эндпоинт встаёт в ту же цепочку middleware;
- **нет алертов** — `recordprobe.Usecase` уже возвращает факт смены состояния,
  отправка уведомления подключается туда как ещё один порт.
